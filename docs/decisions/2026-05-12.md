# 2026-05-12 Decisions

## LLM Provider Contract and Readiness Baseline

Decision: LLM integrations in scaffolded projects start from a provider contract, environment-key declaration, fake fallback, readiness check, and manual gates before live provider adapter code is added.

Reason: Most new projects will want LLM capability quickly, but provider calls involve credentials, cost, generated artifacts, and potential external actions. The scaffold should make the fast path visible and testable without committing secrets or shipping a live adapter in the baseline template.

Implications:

- `contracts/schemas/llm-provider.schema.json` defines the portable provider contract shape.
- `contracts/examples/valid/minimax-llm-provider.json` gives a MiniMax M2.7 starting point.
- `packages/core/src/llm-provider-readiness.ts` checks runtime readiness without making network calls.
- Live SDK or HTTP provider code remains downstream in copied projects.
- Email sending, application submission, publishing, payments, and logged-in browser activity remain manually gated by the owning project.
